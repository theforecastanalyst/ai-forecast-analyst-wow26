Pick your AI

Every technique on this page can work in all four, but some depend on which version you have (free or paid), your settings, and what your company has switched on. For maths, check your version can actually run code first: there's a quick test in Act 2. Here's my take on where each one shines.

Best for work

Microsoft Copilot

What most companies use. It sits inside Outlook, Teams, Word and Excel, and it can work with your work files.

Not the best for code or maths. The free version I tested couldn't run code. Running code may need a paid version, like the Microsoft 365 Copilot many workplaces use. If you have access to GitHub Copilot, use that for code and calculations instead. It's what I use at work.

The all-rounder

ChatGPT

The king of general AI use. It covers almost everything well, but it doesn't specialise.

Check before you do maths. The free version I tested couldn't run code. Running code may need a paid version, including the business versions workplaces use. Run the test in Act 2 before you trust it with numbers.

Technical work and deep thinking

Claude

Great if you're more technical: code, data and analysis. Also very strong at long documents and writing.

My choice at home. I pay for it myself and use it for family use, code work, building apps and agentic tasks. It ran code in my testing. If you have access to it, I recommend it.

If your work runs on Google

Gemini

Built into Gmail, Docs and Sheets, and a strong all-round chat assistant as well.

Ran code in my testing. The free version ran the Erlang C code and got the right answer, but it only let me ask one question before asking me to pay.

The best AI is the one you'll actually use.

At work, use the tool your company has approved and follow its rules for using it. Never paste customer data into any AI tool, especially personal details like names, addresses, phone numbers or account numbers. You don't always know where that data ends up. If you're not sure what's OK to share, check your company's policy.

The skills from the talk

Three parts, in the same order as the talk: how you talk to AI, how much you trust what it gives you, and what you build with it. Each one has the prompts from the slides, ready to copy and use.

The slide prompts are short so they fit on a slide. Treat them as a foundation and build on them. The bigger the question, the more detail it needs.

Act 1

Talk to it

These are the foundations. Without them, nothing else you do with AI will get you the results you want.

They work in any AI tool, including the free versions. You don't need a paid subscription, so anyone can start practising these today.

Prompt engineering

Vague prompts get vague answers. Give it a role, the context, and your constraints, not just a task.

Before
Can you tell me the equation to find out how many staff I need?
After · from the slide
You are a forecast analyst. Can you tell me how to use Erlang C to calculate staffing requirements? I need it at the interval level, and I am trying to achieve a service level of 60% of calls answered in 30 seconds.

Role: who it should act as. Context: what it needs to know. Constraints: the boundaries it works within. For real work, add two more: what success looks like, and the format you want the answer in.

Template · works for any task
You are [role, e.g. an experienced workforce planner].
I need [the task] for [who it is for].
Context: [what it needs to know: the situation, the data, what you have already tried].
Success looks like: [what a great answer would let you do].
Constraints: [targets, limits, rules, length].
Give me the answer as [a table, an email, numbered steps, three options].
See the slide example built out for real work
Built out
You are an experienced workforce planner in an Australian contact centre.
I need to understand how Erlang C works so I can work out staffing requirements myself.
Context: we forecast in 30-minute intervals. I'm comfortable with Excel, but I've never used Erlang C.
Constraints: our service level target is 60% of calls answered in 30 seconds, and we cap occupancy at 85%. Explain it in plain English, without heavy maths notation.
Success looks like: I can explain the method to my manager and I know what data I need.
Give me the answer as:
1. A step-by-step explanation of how Erlang C works.
2. The inputs I need, and where each one usually comes from.
3. How to lay out the data in a spreadsheet for a full day.

This one is about understanding the method. When you're ready to work out the actual numbers, see Estimate vs calculate in Act 2.

Interview me first

You don't always know what detail you're missing. Ask it to question you before it answers. It guesses less, and you'll spot gaps in your own thinking. It works on anything: a forecast, a report, a presentation, a tricky email.

Add this to the end of any prompt
Before you answer, interview me. Ask me up to five questions you need to get this right, most important first. Ask them all at once, then stop. Don't start the task until I've answered. If I don't know an answer, suggest a sensible default and tell me what you assumed.
For bigger tasks
I want to [the task]. Before you start, interview me. Ask one question at a time and wait for my answer before asking the next. Don't start the task until the interview is finished. Ask no more than 10 questions, and I can say "go" at any point. If I don't know an answer, suggest a sensible default. When you have enough, tell me what you've understood and check it with me before you begin.

Use them with any prompt. For a good first try, add one to a prompt you wrote with the template above. All at once is quicker. One at a time goes deeper, because each question builds on your last answer.

See what it might ask you

Add the short version to the Erlang C prompt from the slide, and you might get questions like these:

  • Is your forecast calls offered or calls handled?
  • Does your AHT include wrap time?
  • Should abandoned calls count towards your service level?

If any of those made you stop and think, that's the point. It's finding the gaps in your thinking, not just its own.

Treat it as a conversation, not a search bar

One prompt rarely gets the final answer. Push back, ask follow-ups and refine as you go. The best answer often comes from question 3, not question 1. You'll see a real example of this in Act 2.

When you don't understand it

  • Explain [the part you don't follow] again, more simply.

When you're not sure it's right

  • What assumptions did you make in that answer?
  • What's the weakest part of this answer?
  • What would a sceptical manager ask about this?

When it's close but not quite

  • Give me three different options instead of one.
  • What would change if [something was different]?

When you know it's wrong

  • That doesn't match what I see. In my data, [what you know]. Rework it with that in mind.

If you push back and it instantly agrees, be suspicious. AI often caves even when it was right. Ask it why it changed its answer.

If it gets stuck or goes round in circles, ask it to summarise what you've agreed so far. Then start a new chat with that summary.

Keep using the first two skills as you go. Each follow-up is a prompt too, so be specific, and ask it to interview you again if the task changes.

Level up

You've just taken your AI skills to a new level.

Better prompts, letting it interview you, and treating it as a conversation. Three simple changes, and once you're doing them together, you're working with AI, not just asking it questions.

Now let's take it to the next level: knowing when to trust what it gives you.

Act 2

Trust it

Estimate vs calculate

AI will happily estimate a number instead of calculating it, and the estimate can sound exact. Maths isn't natural for a language model. Make it write and run code. Use this whenever a number will leave your desk: in a report, an email or a decision.

Works for any calculation
Write and run code to calculate this. Don't estimate. Show me the inputs you used and the result, then explain in plain English what the code does. Include the code at the end.

Before you do any maths, make sure your AI can actually run code.

Some tools and versions can't, or have it switched off. Instead of telling you, they write the code and make up the result. Check your tool's settings or ask your IT team, then run this quick test.

Test · does it really run code?
Run this Python code and show me the exact output:
import hashlib
print(hashlib.sha256(b"WOW26").hexdigest()[:10])

The right answer is 198b19a1ed. Nobody can work that out in their head, AI included. If you get anything else, your tool isn't running code, and you shouldn't trust it with numbers.

Check it actually ran the code. A tool saying it ran the code isn't proof. Ask the same question twice: real code gives the same answer every time. Change one input: if AHT goes up, agents should go up. For anything important, paste the code into a new chat or another tool and compare the results.

Check the inputs first. You don't need to read code to catch the most common mistakes: AHT in minutes instead of seconds, the wrong interval length, a target typed wrong.

See a worked example: Erlang C

1 · The prompt I used

Prompt
You are an experienced workforce planner in an Australian contact centre.
I need to work out staffing requirements for next Monday, and I want to understand the method, not just get a number.
Context: we forecast in 30-minute intervals. Our busiest interval is 10:00 to 10:30, with 420 calls forecast and an average handle time of 380 seconds.
Constraints: use the Erlang C formula. Our service level target is 60% of calls answered in 30 seconds, and we cap occupancy at 85%.
Give me the answer as:
1. A plain-English explanation of how Erlang C works, step by step.
2. A worked example using my 10:00 to 10:30 interval.
3. The data I'd need to do this for the whole day, and how to lay it out in a spreadsheet.

2 · What happened

The explanation was good, but it skipped the actual service level calculation and guessed "a bit above 105 agents". Running the real Erlang C formula in code gives exactly 105. The service level target is met at 93 agents, and the 85% occupancy cap is what pushes it to 105. The method was right. The number was a confident guess.

3 · The follow-up: ask it to run code

Follow-up
Now write and run Python code that applies the Erlang C formula to my [10:00 to 10:30] interval. Don't estimate. Show the service level and occupancy for each agent count from [89] to [110], and tell me the smallest number of agents that meets both targets. Show me the inputs you used and the result, then explain in plain English what the code does. Include the code at the end.

The numbers are the ones from my test, so you can check your tool gets 105. Then swap in your own.

4 · What happened next

It wrote correct code, said it had run it, and reported 107 agents. When I pushed it, it said 108, "confirmed by execution". The version I was using (free Copilot) couldn't run code, so it made up the output. Another tool with code running switched on (paid Claude) ran the same code and got 105.

Make sure your AI can actually run code, and always verify your outputs.

Chain it, don't cram it

One giant prompt is one giant chance to get it wrong. A mistake early on carries quietly through to the end. Break it into small steps and check each one before you move on.

When to chain: if your prompt has "and then" in it more than once, break it up.

Cram
Calculate my Erlang C staffing requirement, apply my occupancy cap, add shrinkage and show me what happens at a 50% service level.

Chain · send these one at a time

  1. Write and run code to calculate the Erlang C staffing requirement for my interval.
  2. Check the number, then apply my 85% occupancy cap.
  3. Check the number again, then add my shrinkage to get rostered agents.
  4. Check the number, then show me what happens if my service level target was 50% instead.

What "check" means: does it look right compared with what you know, like last week's actuals? Are the inputs right? Only send the next step when you're happy with this one.

For any task · let it plan the chain
Before we start, break this task into steps. List them, but don't do any yet. Then we'll do them one at a time, and I'll check each one before we move on.

Verification

The answer that sounds right is the most dangerous one. Confidence isn't correctness. Check it against something you trust, or make it check itself using a different method. The Erlang C example in Estimate vs calculate is this in action: an independent calculation caught the guess.

This is the difference between letting AI do its own thing and using it properly at work.

When a number goes into a report, an email or a decision, your name is on it, not the AI's. Checking it is quality assurance, the same as you'd do on any piece of work before it goes out. Get it wrong once and people stop trusting your numbers, whether AI made them or not. Get it right every time and you become the person whose numbers people rely on.

Checking your work was a big part of my Master of Analytics, and it's a foundation of any analyst role, forecasting included. AI doesn't change that. It makes it more important.

For numbers
How would you verify this result? List the checks, then run them using a different method from the one you used to get the answer. Show me each check and its result, and tell me what would make this answer wrong.
For summaries and documents
Check your summary against the source. List anything you included that isn't in the source, and anything important you left out.

Don't let it mark its own homework. If it made a wrong assumption the first time, it may repeat it when checking. For an independent check, paste the result into a new chat so it has no memory of how it got there.

Something you trust could be last week's actuals, a free online Erlang C calculator, or rules that can't be broken: agents must be more than the Erlangs, and occupancy can't be over 100%.

Match the check to the stakes. A quick sense check for your own use. An independent check for anything going to leadership.

You can now get good answers, and you know when to trust them.

The final level: building it into something you can reuse, so you don't start from scratch every time.

Act 3

Build with it

Markdown as a knowledge base

Stop re-explaining your context. Save it once in a markdown file (.md) and give it to the AI every time. Markdown is just plain text: # makes a heading and - makes a list. AI reads and writes it natively.

Let AI write it for you
Interview me about how my team forecasts: our targets, assumptions, definitions, and the things that affect our forecast. Ask one question at a time. Then write it up as a markdown file I can save.
What it might look like · my-forecasting-context.md
# My forecasting context
Last updated: [date]

## Targets
- Service level: [e.g. 60% of calls answered in 30 seconds]
- Occupancy cap: [e.g. 85%]

## Assumptions
- Shrinkage: [e.g. 32%, made up of leave, training, meetings]
- Forecast at the interval level (30 minutes)

## Definitions
- AHT = talk + hold + wrap time

## Things that affect our forecast
- [e.g. end of financial year peak in late June]
- [e.g. marketing campaigns, usually announced two weeks out]
- [e.g. system outages drive repeat calls for 2 to 3 days]

The AI can't see the file unless you give it. Attach it at the start of each chat, or save it somewhere your tool can always see, like a Copilot Notebook or agent.

New to markdown? Markdown Tutorial teaches the basics in about 10 minutes. It's free, and you practise as you go.

Saving it: write it in Notepad, choose "Save as type: All files" and name it something.md. Otherwise Notepad may save it as .md.txt.

Keep it current. If shrinkage changes and the file doesn't, every answer is wrong and still sounds confident. Review it monthly and update the date.

Bonus: the same file is easy for people to read too, and AI can turn it into a polished document or report.

Build your first skill

A markdown file gives AI information. A skill gives it a process: a reusable instruction you teach once and use every time. Knowing how to build skills is the real skill.

In the talk I showed a staffing skill. This one is for everyone: an email writer. It's easy to check, too. You'll know straight away if the draft sounds like you.

email-skill.md
# Skill: Write my work emails

## When to use this
Whenever I ask you to write, reply to, or tidy up an email.

## About me
- I'm a [your role] at [your team or company].
- I usually write to [who: e.g. operations managers, team leaders, executives].

## Before you write
Interview me first. If I haven't already told you, ask me:
1. Who is it to, and what's my relationship with them?
2. What do I need them to know or do after reading it?
3. Is there a deadline, or anything sensitive?
Ask them all at once, then stop. Don't write the email until I've answered.

## How I write
- Tone: [e.g. friendly but direct, no corporate jargon]
- Spelling: [e.g. Australian English]
- Length: [e.g. under 150 words, short paragraphs]
- Greeting: [e.g. "Hi [name]," never "Dear"]
- Sign-off: [e.g. "Cheers, Steve"]
- Words I never use: [e.g. synergy, circle back, per my last email]

## Structure
1. The point or the ask in the first two lines.
2. Only the context they need.
3. A clear next step, with a date if there is one.

## Rules
- Never invent facts, numbers, dates or names. If something is missing, write [CHECK: what's missing] in the draft.
- If the email delivers bad news or pushes back, give me two versions: one softer, one more direct.
- No bullet points unless I ask for them.

## An email I'm happy with
[paste a real email you wrote that sounds like you, with names and anything confidential removed]

## When you're done
Give me the subject line, then the email, then one line on anything you weren't sure about.
Don't want to fill it in yourself?
Here's a skill template. Interview me to fill in everything in [brackets]. Ask one question at a time. When we're done, give me the finished skill, ready to save.

[paste the skill here]

What to customise

  • [About me]Who's writing and who's reading. This sets the level of detail and the vocabulary it uses.
  • [How I write]The biggest lever on sounding like you. Not sure how to describe your style? Paste three emails you've sent and ask: "Describe my writing style as a list of rules I could give an AI."
  • [An email I'm happy with]One real example beats ten rules. Strip out names and anything confidential first.
  • [Rules]Add your own no-gos. Keep the [CHECK] rule: it stops the AI making things up and shows you where to look.

Test it before you trust it

  1. Pick three emails you've already sent.
  2. Give the skill the situation behind each one, not the email itself. For example: "I need to tell the ops manager next week's forecast is up 12% because of the billing change, and ask for 6 extra staff on Monday."
  3. Compare its drafts with what you actually wrote.
  4. Where it's off, ask: "What should I add to the skill so you get this right next time?" Update the skill, then test again. Two or three rounds is normal.

Make a skill for anything

The email skill is a start. The real skill is building your own for the work you do every week: a forecast review, a variance explanation, a weekly report.

Build your own skill
I do [task] regularly. Interview me about how I do it: when I do it, what you'd need from me, the steps, my rules, and what good looks like. Ask one question at a time. Then write it up as a skill I can save.

Then test it the same way: on real examples where you already know what good looks like.

Use it in Copilot

I've used Copilot here because it's what most workplaces use. There are two ways to use a skill in it, depending on what your company has given you. The steps use the email skill, but they work the same for any skill.

  • Option 1 · Attach the fileWorks in any version of Copilot. You attach the skill at the start of each chat.
  • Option 2 · Save it as an agentUses Agent Builder, which most Microsoft 365 licences include, unless your IT team has turned it off. Connecting it to SharePoint and your work data needs a Microsoft 365 Copilot licence. Set it up once and it's always ready, with no attaching. If you can see "New agent" in Copilot, you can use it.
  1. Paste the skill into Notepad, fill in the brackets, and save it as email-skill.md in your OneDrive. Choose "Save as type: All files", or Notepad may add .txt to the end.
  2. In Copilot Chat, select + and attach the file.
  3. Say: "Follow the instructions in this file. I need an email to…"

Want your writing style in every chat? Paste the "How I write" section into Copilot's custom instructions (Settings → Personalisation), if your organisation has it turned on.

  1. In Microsoft 365 Copilot, select New agent, then Skip to configure.
  2. Name it "Email writer" and give it a one-line description.
  3. Paste your customised skill into Instructions (up to 8,000 characters).
  4. Use the Try it panel to run your three test emails, then create it.

It now sits in your agent list, ready whenever you need it.

Using something else? In ChatGPT, use a Project or a custom GPT. In Claude, a Skill or a Project. In Gemini, a Gem. Same instructions, different place to save them.

The staffing skill from the talk · for forecast analysts
erlang-c-skill.md
# Skill: Erlang C staffing calculator

Whenever I ask you for staffing calculations:
- Always use the Erlang C formula. Never estimate.
- Work at the interval level, not daily or weekly.
- Ask me for call volume, AHT and my service level target.
- Write and run code to calculate the result.
- Chain it: base requirement, then occupancy, then shrinkage.
- Before the final answer, explain how you verified it.

Notice what's in it: everything from the talk, saved once so it happens every time.

This is the short version from the slide, not a finished skill. A real one needs your targets, your data layout, your shrinkage rules and how you check the result. Use the "Build your own skill" prompt above to build it out properly: paste this in as your starting point and let it interview you.

When you're ready: agents

Start with skills. An agent is just skills chained together and given permission to run on their own. It plans the steps, acts, checks its own work, and loops back if the check fails.

Not the same as the Copilot agent above. A Copilot agent from Agent Builder is a saved skill you still start yourself. The kind of agent here runs on its own, without you starting it.
